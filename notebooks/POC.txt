I want to build a Python proof of concept that converts exported PathWise HTML model documentation into a machine-readable dependency graph.

## Background

The PathWise model documentation contains a hierarchical structure similar to:

* Model

  * Data Sources

    * market_data
    * inforce
    * params
    * actuarial assumptions
    * etc.
  * Model Libraries

    * Library

      * Inputs
      * Calculations

        * Dictionary
        * Computation
        * Projection
      * Outputs
      * User-defined functions
  * Project-level Calculations

    * Dictionary
    * Computation
    * Projection
  * Project-level User-defined functions
  * Calculation Results

Inputs, calculations, projections, and outputs contain expressions that reference other model objects.

Examples of relationships may look conceptually like:

`N_HYBRID_INDEX = Constants.N_HYBRID_INDEX`

or

`forward_rate = Projection.revised_short_rate`

or a formula may reference several variables and/or call a user-defined function.

The exported HTML also appears to contain hyperlinks between referenced model objects. If hyperlinks contain resolved target information, prefer using the hyperlink target instead of trying to infer the target from text.

## Goal

Build a Python parser that automatically extracts:

1. model components/nodes
2. direct dependency relationships/edges
3. variable aliases / mappings where possible
4. downstream dependency impact using graph traversal

Do NOT manually generate complete dependency paths. Only extract direct relationships. Complete downstream paths should be derived programmatically from the direct-edge graph.

## 1. First define the reference-resolution problem

PathWise references may appear in several forms:

### A. Hyperlink-resolved references
The HTML may contain an `<a href>` or anchor pointing directly to the referenced object.

These should have the highest priority.

### B. Fully qualified Library references

Examples may conceptually look like:

`Lib.InterestRate.Output.forward_rate`

or another fully qualified library/object path.

### C. Relative references inside the current Library

Examples:

`Projection.factor`

`Dictionary.some_parameter`

`Computation.some_value`

These should resolve relative to the current library and calculation block.

### D. Direct Data Source references

Examples:

`inforce.investment_account`

`market_data.some_curve`

`product_info.product_code`

These may appear without any `Lib.` prefix.

They should resolve to existing DATA_SOURCE or DATA_SOURCE_FIELD nodes when the first namespace matches a known Data Source.

### E. Project-level Calculation references

Examples may refer to centralized project calculations such as:

`RateSetting.xxx`

`Cashflow.xxx`

or other project-level calculations.

These must be distinguishable from Libraries and Data Sources.

### F. Project-level UDF references

A function call may resolve to a project-level user-defined function.

### G. Library-level UDF references

A function may resolve only within the current library.

### H. Local variables / current calculation block variables

A symbol may refer to a locally defined variable within the same Dictionary, Computation, Projection, or calculation block.

### I. Built-in PathWise / language functions

Examples may include:

`prev`

`exp`

`min`

`max`

or other built-in functions.

These should NOT become UNKNOWN nodes or unresolved model references.

### J. Array/index references

Examples:

`foo[idx]`

`market_roll_forward[roll_forward_index[step]].swap_rate`

The resolver should identify the meaningful model objects without treating every index expression or numeric literal as a model dependency.

### K. Dynamic or ambiguous references

If the reference cannot be safely resolved using static information, preserve it as unresolved.

Do NOT guess.
